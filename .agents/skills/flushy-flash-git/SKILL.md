# Flushy Flash — git workflow

Project-specific rules. Where a general-purpose git skill disagrees with this
file, **this file wins** — it knows the repo's actual CI, secrets and release
mechanics.

## Never commit these

Checked before every `git add`:

| Pattern | Why |
|---|---|
| `*.keystore`, `*.jks` | The Android signing key. Leaking it lets anyone ship a malicious update that installs over the real app. Losing it means you can never update installed apps again — **keep an offline backup**. |
| `service-account*.json` | Full Firebase admin access. A genuine secret. |
| `google-services.json`, `GoogleService-Info.plist` | Not strictly secret, but this repo is **public** and published Firebase API keys get scraped for signup spam and quota burn. CI reads them from the `GOOGLE_SERVICES_JSON` secret. |
| `.env.local` | May contain `GOOGLE_APPLICATION_CREDENTIALS`. |
| `android/`, `ios/` | Generated by `expo prebuild`. Committing them breaks CNG. |

All are in `.gitignore`. If one appears in `git status`, stop and ask — do not
`git add -f`.

## Verify before committing, not after

Run the gate from AGENTS.md §9 **before** creating the commit. CI runs the same
block, so a failure here is a failure there:

```bash
npm run typecheck                          # app
npx tsc --noEmit -p scripts/tsconfig.json  # node scripts
npm run lint                               # includes the import firewall
npm test
npx expo-doctor                            # SDK drift
```

Additionally, when the change touches:

- **`firestore.rules` / `storage.rules` / `database.rules.json`** →
  `npm run test:rules`. Non-negotiable: the rules are the app's only real
  security boundary.
- **`app.json`, a config plugin, or a native dependency** → say so in the commit
  body. It means everyone needs a fresh `npx expo prebuild --clean` and dev build.
- **UI, map or location code** → verify on a device or emulator. Typecheck and
  lint cannot see a blank map.

## Branching — GitHub Flow

`main` is protected: PRs only, CI must pass. **Never commit directly to `main`**,
and never force-push a shared branch.

```bash
git switch -c feat/review-composer
```

| Prefix | For |
|---|---|
| `feat/` | New features |
| `fix/` | Bug fixes |
| `chore/` | Deps, CI, docs, tooling |

## Commit messages

Conventional commits. **The subject line matters more than usual here**: PR
titles become the release notes that students read, so write for someone who was
not involved.

```
type(scope): imperative summary under ~72 chars

Why the change was needed, and anything non-obvious about the approach.
Explain trade-offs and rejected alternatives — the diff already shows what
changed, so spend the body on why.

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

Types: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `ci`, `perf`.
Useful scopes: `map`, `auth`, `rules`, `ui`, `seed`, `ci`.

Good: `fix(map): stop building pins drifting at zoom > 17`
Bad: `fix bug`, `updates`, `wip`

Split unrelated changes into separate commits. Do not bundle a dependency bump
with a feature.

Issue linking (`Fixes #12`) is welcome but **not required** — this repo does not
run an issue-first process.

## Pull requests

`.github/pull_request_template.md` has the checklist. Label the PR so it lands in
the right release-notes section (`.github/release.yml`): `feature`, `fix`,
`security`/`rules`, `chore`/`ci`/`docs`.

`gh` is not installed by default on the maintainer's machine
(`winget install GitHub.cli`). Without it, open PRs in the browser.

## Cutting a release

Releases are **tag-triggered**. Pushing to `main` does not publish anything.

```bash
# on main, CI green
npm version minor --no-git-tag-version     # updates package.json
# set expo.version in app.json to match
git commit -am "chore: release v1.1.0"
git tag v1.1.0
git push origin main --tags
```

`.github/workflows/release.yml` then prebuilds, builds a signed APK, verifies it
is **not** debug-signed, and publishes a GitHub Release with auto-generated notes
and the APK attached.

`versionCode` comes from the workflow run number, so it always increases — Android
requires that for in-place upgrades. Do not set it by hand in `app.json`; the
workflow overwrites it.

A release will fail without these repo secrets: `GOOGLE_SERVICES_JSON`,
`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
`ANDROID_KEY_PASSWORD`.

## Do not

- Rewrite published history (`push --force`, `rebase` of pushed commits)
- `git add -A` without reading `git status` first
- Amend a commit that is already pushed
- Commit generated output: `android/`, `ios/`, `node_modules/`, `uniwind-env.d.ts`
